# ОСНОВЫ MAKCU: ПОДКЛЮЧЕНИЕ ПО UDP И НАСТРОЙКИ ПЛАТЫ

Этот документ и папка `basics/` созданы для того, чтобы с нуля, без оверинжиниринга и предположений разобрать архитектуру взаимодействия с платой MAKCU.

---

## 1. КАК ОСУЩЕСТВЛЯЕТСЯ ПОДКЛЮЧЕНИЕ ПО UDP

### Физический и сетевой уровень
1. **Топология:**
   - ПК подключен к Ethernet-сети (через коммутатор/роутер или напрямую).
   - Плата MAKCU (чип ESP32-S3 с USB-Ethernet адаптером RTL8152) находится в той же локальной подсети.
   - **IP платы:** `192.168.50.175`
   - **UDP-порт:** `8080`
2. **Отсутствие рукопожатий (Handshake):**
   - UDP — протокол без установления соединения (Connectionless).
   - В отличие от TCP (SYN -> SYN-ACK -> ACK), в UDP нет сессий, авторизаций и рукопожатий.
   - Любой компьютер в сети может сразу отправить датаграмму на `192.168.50.175:8080`.
   - Если формат пакета корректен, ESP32-S3 принимает его и немедленно исполняет.

## 2. СТРУКТУРА ПАКЕТА UDP НА УРОВНЕ БАЙТОВ (UdpWireMode.RAW)

Плата ожидает пакеты в формате **RAW UDP framing** спецификации `mak-suite`.
Каждый UDP-пакет состоит из 3 слоев:

```
+---------------+------------------------+------------------------------------+
| Sync (1 байт) | Nonce транзакции (8 б) | Кадр MAK_API (4+ байта)            |
|     0x55      |  случайные 8 байт      | DE AD | LEN:u16 | CMD:u8 | PAYLOAD |
+---------------+------------------------+------------------------------------+
```

### Разбор каждого байта:
1. **`0x55`** (1 байт) — синхробайт режима RAW UDP. Указывает сетевому парсеру ESP32, что пакет идет без шифрования в формате с транзакционным nonce.
2. **`Nonce`** (8 байт) — случайные 8 байт (`secrets.token_bytes(8)`). Плата копирует этот же nonce в ответный пакет, чтобы клиент сопоставил ответ с запросом.
3. **`0xDE 0xAD`** (2 байта) — сигнатура начала кадра `MAK_API`.
4. **`LEN`** (2 байта, Little-Endian `uint16`) — длина поля данных `PAYLOAD` (НЕ включает байт `CMD`).
5. **`CMD`** (1 байт) — бинарный опкод команды.
6. **`PAYLOAD`** (`LEN` байт) — аргументы команды.

## 3. БАЗОВЫЕ ОПКОДЫ ПЛАТЫ MAKCU (СПЕЦИФИКАЦИЯ MAK_API)

Никаких текстовых строк типа `"m.move_now"` для базовой работы не требуется. В прошивке зашиты бинарные опкоды:

| Опкод | Название команды | LEN | Аргументы (Payload) | Ответ от платы |
|:---:|:---|:---:|:---|:---|
| **`0x02`** | `GET DEVICE` | 0 | *нет* | 1 байт: битовая маска устройств (`0x01`=Мышь, `0x02`=Клавиатура) |
| **`0x04`** | `GET FIRMWARE` | 0 | *нет* | 4 байта (`uint32`): номер сборки прошивки (например, `4076`) |
| **`0x18`** | `SET MOVE` | 4 | `dx: int16`, `dy: int16` (Little-Endian) | *нет (исполняется сразу)* |
| **`0x11`** | `SET LEFT_BTN` | 1 | `state: uint8` (1 = нажать, 0 = отпустить) | *нет* |
| **`0x12`** | `SET RIGHT_BTN`| 1 | `state: uint8` (1 = нажать, 0 = отпустить) | *нет* |
| **`0x3E`** | `CONNECTION` | N | Пакет управления настройками NOR Flash | Зависит от подкоманды |

### Пример: Пакет сдвига мыши на `dx=+20`, `dy=-10` (Опкод `0x18`):
```python
import struct, secrets

dx = 20
dy = -10
payload = struct.pack("<hh", dx, dy)          # 4 байта: 14 00 F6 FF
frame = b"\xDE\xAD\x04\x00\x18" + payload     # 9 байт: DE AD 04 00 18 14 00 F6 FF
packet = b"\x55" + secrets.token_bytes(8) + frame # Итого 18 байт в сокет
```

## 4. ДЕФОЛТНЫЕ НАСТРОЙКИ ПЛАТЫ MAKCU (ФАКТИЧЕСКИЕ ДАННЫЕ ИЗ NOR FLASH)

Мы считали фактический слепок памяти настроек прямо с подключенной платы (`DeviceConfiguration` / Opcode `0x3E`):

### 1. Аппаратные дескрипторы USB Device (к ПК):
- **Эмулируемое устройство:** Ресивер Logitech G PRO Wireless (VID `0x046D`, PID `0xC547`).
- **HID Дескриптор:** `R:MK;M:8uf;K:8uf;C:0uf`
  - `M:8uf`: Частота опроса мыши USB Interrupt IN = **1000 Гц** (8 микрофреймов = 1.0 мс `bInterval=1`).
  - `K:8uf`: Частота клавиатуры = 1000 Гц.
- **Внутренний UART платы (между чипами):** `4 000 000` бод.
- **Виртуальный COM-порт:** Аппаратно отключен (`m.port(0)`), чтобы исключить прерывания UART.

### 2. Настройки очереди и фильтрации (ФАКТИЧЕСКИЙ АНАЛИЗ NOR FLASH):
> [!IMPORTANT]
> **Параметры `buffer_ms` и `interpolation: auto / fixed / off` НЕ ОТНОСЯТСЯ К МЫШИ!**
> Аппаратный запрос `DeviceConfiguration.info()` возвращает `sections: SettingsSection.MOUSE (маска 4)`.
> Секция `SettingsSection.CONTROLLER` (маска 1) на плате MAKCU Mouse/Keyboard **аппаратно не поддерживается** (при попытке записи возвращается ошибка `status 5: Unsupported`).
> Поля `buffer_ms`, `interpolation`, `behaviors` и `translation` в SDK `mak-suite` относятся исключительно к аналоговым стикам геймпада (Xbox / DualSense / GIP).

**Реальные параметры мыши в NOR Flash:**
- **`mouse_spread_percent` (секция `SettingsSection.MOUSE`, маска 4):**
  - *Заводское значение по умолчанию:* **`50%`**.
  - *Текущее значение на плате:* **`0%`** (перманентно сохранено в NOR Flash).
  - *Что делает этот параметр:* В официальной документации `mak-suite` это настройка *"mouse injection interpolate"*:
    - При `50%` прошивка накладывает сплайн и размазывает дельту каждого пакета на окно **~17 мс**.
    - При `0%` аппаратный сплайн полностью отключен, дельты отдаются дискретными субстепами без искусственной задержки.

### 3. Как на самом деле работает планировщик инжекции в FreeRTOS на ESP32-S3:
- **Квант субстеппера (2.0 мс / 500 Гц):**
  Задача синтетического инжектора `Mouse Injection Task` на чипе Device тактируется с дискретностью **2.0 мс**.
  Когда с ПК приходит 8-миллисекундный UDP-пакет (125 Гц), плата нарезает его на $\frac{8\text{ мс}}{2\text{ мс}} = 4$ субстепа по 2 мс.
  Поэтому Windows Raw Input фиксирует частоту **500 Гц** (интервалы ~2.0 мс).
- **Причина сваливания в 125 Гц (Queue Underflow):**
  Если ПК отправляет пакеты строго «впритык» каждые 8.0 мс без упреждающего буфера, любая задержка доставки пакета или тика планировщика приводит к полному опустошению очереди на ESP32.
  При опустошении буфера прошивка переходит в режим аварийного наверстывания (Catch-up / Immediate Flush) и сбрасывает следующий задержавшийся пакет в **один USB-отчет** (1 субстеп = 1 UDP-пакет), из-за чего частота падает с 500 Гц до 125 Гц.
- **Устранение сваливания (Lead Pre-buffering):**
  ПК отправляет первый кадр движения с упреждением (создавая запас в 1 кадр в очереди ESP32). В буфере платы всегда находится 1 готовый кадр, очередь никогда не опустошается, и частота 500 Гц не проседает.

## 5. ПОЧЕМУ ПРОИСХОДИЛИ СБОИ В ПРОШЛЫХ ВЕРСИЯХ

1. **Оверинжиниринг с нейросетью:**
   В код подмешивалась модель тремора рук ABCurves H80 через C-DLL. Когда пользователь двигал физическую мышь своей реальной рукой, реальный тремор складывался с синтетическим тремором модели, создавая хаотичные броски.
2. **DWM троттлинг Windows и искусственный 2.17x масштаб:**
   В старом коде стоял множитель `2.17`, рассчитанный на то, что Windows DWM троттлит фоновые окна до 125 Гц. При движении рукой прерывание будило DWM до 1000 Гц, и завышенный масштаб раздувал круг в 3 раза на пол-экрана.
3. **Текстовые команды вместо опкодов:**
   Попытки обойти 8-мс очередь через текстовый `m.move_now` требовали специального текстового опкода `0x6B`. Любая ошибка в форматировании ломала прием пакетов.

## 6. МИНИМАЛЬНЫЙ РАБОЧИЙ ПРИНЦИП

Для идеальной, стабильной работы без срывов достаточно:
1. Открыть обычный UDP сокет.
2. Слать напрямую бинарный опкод **`0x18`** (`SET MOVE`).
3. Не трогать маски мыши (рука свободна).
4. Держать темп 100–500 Гц с микросекундным таймингом.
