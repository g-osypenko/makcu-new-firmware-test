# MAKCU mover (COM): эталонная инжекция 1000 Гц + ABCurves Renderer

**Статус на 2026-10-10: работает.** На прошивке MAKCU 4094 инжект идёт с частотой
~1000 Гц (99.7–100% интервалов по 1 мс), путь «отправлено = пришло в Windows»
совпадает до отсчёта, касание реальной мыши траекторию не ломает (проверено
визуально пользователем). Ключ к этому — команда **Raw movement `0x69`/`0x6A`**
вместо `MOVE 0x18`. Полный разбор: как нашли решение, протокол, все замеры,
риски — в [SOLUTION_1000HZ_RAW_MOVE.md](SOLUTION_1000HZ_RAW_MOVE.md).

Этот README — главный документ папки и точка входа для следующей сессии.
`HANDOFF_PROMPT.md` — история, описывает состояние **до** решения.

---

## 1. Как работает (конвейер)

```
 источник движения                сейчас: Trajectory::at(t) - захардкоженные фигуры
 (позиция как функция времени)    дальше: внешние траектории (план следующего чата)
        │  каждые 1 мс: гладкое намерение Δp = p(t_k) - p(t_k-1), double, оси мыши (Y вниз)
        ▼
 ABCurves Renderer                препроцессинг траектории ПЕРЕД отправкой в MAKCU:
 (abc_renderer.h)                 Δp -> целочисленный отчёт (dx,dy) с "текстурой" настоящего
                                  сенсора: в какие мс отчёт есть, как квантуются отсчёты,
                                  микродрожание. Часто (0,0) - это нормально. Дробный остаток
                                  копится внутри, суммарный путь сохраняется.
        │  ненулевой отчёт (без рендерера: dx = round(p) - уже_отправлено)
        ▼
 RawComTransport, RawMove         0x69 RAW_MOVE на каждый отчёт + квитанции 0x6A,
 (makcu_transport.h)              окно 12 записей, перенос отказанных дельт, свой
                                  overlapped COM-handle, без блокировок потока тайминга
        │  COM5, CH343, 4 000 000 бод
        ▼
 MAKCU fw 4094                    FIFO -> РОВНО ОДИН HID-отчёт на запрос, сложенный с
                                  физическим движением мыши в этом же отчёте
        │  USB; ПК опрашивает MAKCU с интервалом клонированной мыши (1 мс)
        ▼
 Windows / приложение             ~1000 отчётов/с, путь точный
```

Следствия:
- **Частота HID = частота ненулевых команд** (не выше опроса USB). Для 1000 Гц нужна
  ненулевая дельта каждую 1 мс. Рендерер сам решает, в какие мс отчёт есть: его
  нулевые отчёты = миллисекунды без отчёта, как у настоящей мыши.
- Рендерер - это препроцессинг: он не знает про MAKCU, а MAKCU не знает про
  рендерер. Raw-путь доносит каждый отчёт рендерера 1:1. Старый путь `0x18`
  перемешивал их своим интерполятором, поэтому раньше рендерер не работал как задумано.
- Мышь в host-порту MAKCU должна опрашиваться на 1000 Гц: плата клонирует её
  интервал опроса (с мышью 125 Гц инжект не выше 125 Гц).

## 3. Встраивание в свою программу (минимальный каркас)

```cpp
#include "makcu_transport.h"
#include "abc_renderer.h"
using namespace mover;

// --- один раз ---
tuneProcessForTiming();                         // mover_common.h
RawComTransport tx;
std::string err, info;
if (!tx.open("COM5", err)) { /* порт занят / плата не ответила */ }
tx.setFormat(RawComTransport::Format::RawMove);
if (!tx.prepareRaw(info)) {                      // метаданные 0x6A(id=0)
    tx.setFormat(RawComTransport::Format::Mak);  // прошивка без Raw API: 0x18 (~640 Гц)
}

AbcRenderer abc;
std::vector<Report16> profile;
abc.loadModel("ABCurves/models/renderer_global_h80.bin", err);
AbcRenderer::readProfileCsv("profiles/human_start_256.csv", profile, err);
abc.prepareProfile(profile, err);                // ~3 мс, вне горячего пути

// --- на каждый поток движения (прогон/жест) ---
abc.beginEvent(seed, err);
// Поток тайминга (tuneTimingThread + PreciseWaiter), тик k каждые 1 мс по QPC:
//   Point d = source.intent(k);                 // гладкое смещение за эту мс (double)
//   Report16 r{};
//   abc.step(d.x, d.y, r);                      // часто r = (0,0)
//   pendX += r.dx; pendY += r.dy;
//   if ((pendX || pendY) && tx.move(clamp16(pendX), clamp16(pendY))) pendX = pendY = 0;
//   // move() == false: окно/кольцо заняты - дельта остаётся в pend и уйдёт следующим тиком
// Если поток опоздал на несколько мс - шагнуть рендерер на КАЖДУЮ пропущенную мс
// (его часы - это 1-мс отсчёты), а отчёты склеить в одну отправку (так делает runMotion).
tx.finish();                                     // дождаться квитанций, дослать перенос (до 300 мс)

// --- в конце ---
tx.close();
```

Готовый образец этого цикла - `runMotion()` в `motion_engine.h` (ветка `renderer`).
Статистику Raw даёт `tx.extraStats()`: в норме «отправлено = принято в FIFO = отдано
в USB-endpoint», отказов 0, перенос (0,0).

## 4. Сборка и запуск

```
build.bat                         # MinGW-w64 g++ 15 (C:\mingw64\bin), CMake для SDK
makcu_mover.exe                   # меню F-клавиш, транспорт rawmove по умолчанию
makcu_mover.exe --help
```

**Перед запуском** закрыть другой `makcu_mover.exe`: COM5 эксклюзивный, а `build.bat`
не перезапишет запущенный exe. **Выход - END** (не убивать процесс: так возвращается
«Повышенная точность указателя»).

### Как читать вывод

- `HID ... Гц` - LL-хук, каждый отчёт мыши, который увидел Windows (рука = ~990 Гц).
- `отчётов на команду` - 1.00 у raw; > 1 значит прошивка режет команду (старый путь).
- `путь xN.NN` / `Путь: отправлено (...) пришло (...)` - сумма отсчётов Raw Input; без руки должно совпадать.
- `raw 0x69: ...` - квитанции платы: отправлено / принято в FIFO / отдано в USB-endpoint / отказ / немедленные ошибки (нет места) / ack и повторы / окно max / ждали окно / перенос / последняя причина отказа.
- `отложено` - тиков, когда транспорт был занят (дельта ушла следующим тиком).

| Эхо KM (`km.echo()`) | 0 | мутации молчат (нужно для raw/km без лишнего трафика) |

| Блокировки физического ввода (`km.lock_*`, маски) | все 0 | физическая мышь ничем не заблокирована |
| Виртуальный экран (`km.screen()`) | 1920×1080 | только для `km.moveto`/`km.getpos`, нам не нужен |
| Raw API (`0x6A` id=0) | schema 1, `last_accepted_id` 92782, **свободно 16 из 16** | id сбрасываются при перезагрузке платы |
| Настройки (SDK) | sections `0x04` (только mouse), kinds `0x03`, save_state 0, revision 2486104977 | контроллер не подключён - секции контроллера по умолчанию |

## 7. Правила и подводные камни

- **Не смешивать `0x18`/`km.move` и raw** в одном потоке: raw ждёт, пока опустеет очередь AUTO.
- **Raw-квитанции обязательны**: у платы максимум 16 живых/непрочитанных записей; без
  `0x6A consume=1` после 16 запросов плата начнёт отвечать «нет места».
- **ID raw строго растут в пределах загрузки платы** и общие для всех программ на этом
  COM/UDP. Перед работой - `prepareRaw()` (берёт `last_accepted_id`). После перезагрузки
  платы счёт начинается заново - снова `prepareRaw()`.
- **Неподтверждённые квитанции живут на плате до её перезагрузки** и занимают её 16 мест.
  Найдено при снимке 2026-10-10: 3 записи (id 64886–64888, state 2 «отдано в USB»), хвост
  прерванного прогона - скорее всего, консоль закрыли крестиком посреди прогона и процесс
  был убит до `finish()`. Подтверждены вручную. Защиты в коде: обработчик закрытия консоли
  ждёт до 2 с, пока прогон остановится и вызовет `finish()`; `prepareRaw()` подтверждает
  окончательные записи среди последних 4096 id и ставит окно = min(12, свободно − 2);
  запись не затирает слот `id % 64`, пока в нём висит старая. Полностью очищает только
  перезагрузка платы (переподключение USB) или подтверждение точного id.
  Проверить: `--probe` или `--dump-settings` → строка `0x6A ... свободно N/16`.
- **Дельта, не влезающая в поле X/Y дескриптора, отклоняется** (reason 17), плата её не
  режет. Текущий код этого не учитывает (см. раздел 8).
- **Частота HID = частота ненулевых команд.** Стоящая траектория = нет отчётов (как у
  настоящей мыши).
- Мышь в host-порту - 1000 Гц, иначе потолок = её опрос.
- Частоту смотреть LL-хуком или внешним тестером в фокусе; Raw Input фонового окна в
  Windows 11 прореживается (~125 сообщений/с), суммы дельт при этом верные.
- `Device::mouseMove()` из SDK в горячем пути не использовать (блокировки до десятков мс).
- Интерполяция `0x1F` (= «Mouse injection» в app.makcu.com) на raw не влияет. Заводское
  значение AUTO (255); на этой плате сейчас 0 (см. раздел 6).
- Выход только через END/ESC/Ctrl+C - иначе не вернётся «Повышенная точность указателя».

## 8. Что не проверено и план следующего чата

Следующий шаг (по словам пользователя): **убрать захардкоженные траектории** - движение
будет поступать снаружи, логика станет сложнее. Что важно сохранить при переделке:
1. Источник движения должен отдавать **гладкое намерение на каждую 1 мс** (или позицию
   как функцию времени) - это вход рендерера. Рендерер шагать строго раз в 1 мс, включая
   пропущенные ОС тики.
2. Цикл тайминга - абсолютная сетка QPC, без `Sleep`-дрейфа, без блокировок на I/O
   (как `runMotion`). Перенос дельты при `move() == false`.
3. Транспорт - `RawComTransport` + `Format::RawMove`, `finish()` при завершении
   потока движения, `prepareRaw()` при старте и после переподключения платы.
4. На каждый новый поток движения - `beginEvent(seed)` у рендерера.

Не проверено / открыто:
- формальный `--touch-test --hz 1000` на raw с итоговой таблицей (есть только визуальная проверка);
- частота HID, когда рука и инжект двигаются одновременно;
- долгий прогон 10+ мин на 1 кГц (производитель Raw API это тоже не проверял);
- нарезка дельты по границе поля X/Y дескриптора (reason 17 сейчас уйдёт в бесконечный
  перенос, если одна дельта больше поля; на 1 кГц дельты малы, риск - догон после фриза ОС);
- поведение при перезагрузке платы посреди потока (возможен повтор неподтверждённых дельт);
- закрытие консоли посреди прогона после исправления обработчика (проверено только сборкой);
- две программы с Raw API одновременно (общие ID).
