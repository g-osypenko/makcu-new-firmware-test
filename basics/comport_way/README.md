# MAKCU mover — COM-путь, 500–2000 Гц

Инжекция движения через MAKCU по COM (CH343, 4 Мбод) с упором на стабильность
скорости и частоту HID-отчётов > 700 Гц.

## Файлы

| Файл | Что внутри |
| --- | --- |
| `makcu_mover.cpp` | `main`: CLI, пресеты на F-клавишах, живая статистика, итоговый отчёт |
| `motion_engine.h` | расписание по QPC, траектории, суб-пиксельный аккумулятор, всплеск-тест |
| `makcu_transport.h` | транспорты: `raw-async` / `raw-sync` (overlapped COM) и `sdk-mouseMove` |
| `rawinput_monitor.h` | сверка суммы пути через Raw Input (частоту не меряет — см. ниже) |
| `mover_common.h` | часы QPC, ожидание, приоритеты и EcoQoS, отключение акселерации |
| `build.bat` | сборка (MinGW g++ + `libmakxd-cpp.a`; если SDK не собран — собирает его) |

## Сборка и запуск

```
build.bat
makcu_mover.exe --check      # связь + тест тайминга на MOVE(0,0), курсор не двигается
makcu_mover.exe              # меню с горячими клавишами
makcu_mover.exe --run --hz 1000 --pattern line --duration 20   # один прогон без меню
makcu_mover.exe --help
```

## Горячие клавиши (глобальные, тестер поллинга может быть в фокусе)

| Клавиша | Режим |
| --- | --- |
| F1 | 1000 Гц, spread 0%, 30 с — минимальная задержка |
| F2 | 250 Гц, spread 0%, 30 с — рекомендуемый |
| F3 | 125 Гц, spread 50%, 30 с — сглаживание ~17 мс |
| F4 | 125 Гц, spread 0%, 30 с |
| F5 | перебор 125–2000 Гц, мышь не трогать |
| F6 | перебор после касания (первые 6 с коснуться мыши) |
| F7 | 250 Гц, spread 0%, линия 60 с — тест с рукой |
| F8 | 125 Гц, spread 50%, линия 60 с — тест с рукой |
| F9 | сменить траекторию: circle → eight → line |
| F11 | mouse spread по кругу 0/5/10/25/50/100 % (live, без NOR; при выходе возвращается) |
| ESC / та же F-клавиша | стоп прогона |
| END | выход (настройки возвращаются) |

**Поллинг смотреть только во внешнем тестере.** Консоль во время теста в
фоне, а Windows 11 ограничивает Raw Input фоновых окон (~125 Гц, сообщения
склеиваются). Программа показывает здоровье отправки (команд/с, отложено,
опоздание) и сверку суммы пути.

## Результаты замеров (прошивка 4094, 2026-10-10)

Замер — LL-хук мыши (калибровка: рука = ~990 Гц, 99% интервалов по 1 мс),
путь — сумма сырых отсчётов Raw Input на монотонном движении (`ramp`).

**Сторона ПК идеальна:** 250–3000 команд/с без отложенных, опоздание < 0.2 мс.

**Частоту выдачи инжекта задаёт прошивка, и она «учится» на реальной мыши.**
При любой частоте команд (250–3000/с) и любой скорости (1–16 пикс/мс) выход
держится на уровне, который зависит только от того, как перед этим двигалась
реальная мышь:

| Последнее движение рукой | HID инжекта | интервалы |
| --- | --- | --- |
| давно не трогали / резкое движение | ~615 Гц | 1 и 2 мс вперемешку |
| резкое движение (другой раз) | ~420–460 Гц | ~2 мс |
| медленное касание | ~250–320 Гц | 3–4 мс |

Режим держится, пока реальная мышь снова не двинется (не сбрасывается ни
паузой, ни перезапуском программы, ни минутой простоя). Выше ~615 Гц инжект
на стоковой прошивке не выходит ни в одном режиме. Во время инжекта даже
движение руки приходит реже (~460 Гц вместо 1000).

**Потери пути:** при ≤ 1000 команд/с путь доставляется точно (1.00) во всех
режимах. При 3000 команд/с в режиме ~615 Гц теряется 53–59% движения. Это и
было «курсор быстрее и шире после касания»: смена режима меняла долю потерь.
Поэтому эталонный режим — **1000 команд/с, без оверсэмплинга**.

**Чего со стороны ПК сделать нельзя:** поднять частоту инжекта выше темпа
прошивки и не дать ей опускаться после касания. Для этого нужна другая
прошивка: исправление от автора MAKCU или альтернативная с явно заданным
темпом выдачи (например, medius: `EmitPace::Interval/Fixed`).

## Как устроено и почему

**SDK и горячий путь.** mak-suite SDK используется для поиска порта,
handshake (`DEVICE`), версии прошивки и настроек (`mouse spread`).
`Device::mouseMove()` для 1000 Гц не подходит: SDK открывает порт
синхронно, а его поток-слушатель и монитор соединения обращаются к тому же
handle. Windows сериализует такой I/O. Замер на этой машине при 1000 Гц:
| Транспорт | Вызов, ср | Вызов, max | Успел за 2 с |
| --- | --- | --- | --- |
| SDK `mouseMove` | 2044 мкс | 22 391 мкс | 829 из 2000 |
| raw-sync | 133 мкс | 291 мкс | 2000 из 2000 |
| raw-async (overlapped) | 2 мкс | 79 мкс | 2000 из 2000 |

Поэтому после handshake SDK закрывает порт, и программа открывает свой
overlapped-handle. Кадр собирается по MAK_API (`DE AD 04 00 18 x y`,
опкод из `makxd::ApiOpcode::MOVE`).

**Стабильность скорости (не зависит от реальной мыши и подтормаживаний ОС):**
1. Положение — функция времени `p(k·T)`. Дельта тика считается как
   `round(p) − уже_отправлено`, поэтому ошибка округления не накапливается.
2. Сетка тиков абсолютная (`t0 + k·T` по QPC), без дрейфа от `Sleep`.
3. Если поток опоздал меньше чем на период, дельта всё равно считается по
   номинальному времени тика. Шаги остаются одинаковыми.
   Пропущенные тики догоняются одной дельтой. Фриз дольше 25 мс ставит
   траекторию на паузу вместо прыжка.
4. Если драйвер занят, дельта не встаёт в очередь (никаких пачек), а уходит со
   следующим тиком. Сумма пути при этом сохраняется точно.
5. **«Повышенная точность указателя» отключается на время работы** (только
   для текущей сессии, возвращается при выходе; `--keep-accel` отменяет).
   Это главная причина «курсор ускоряется, когда трогаю мышь». С включённой
   акселерацией Windows считает скорость по сумме дельт в каждом HID-отчёте.
   Когда дельты руки и инжекта складываются в одном отчёте, кривая Windows
   нелинейно меняет и вклад инжекта. На Raw Input (игры, тестеры) она не
   влияет.
6. Процесс получает HIGH, поток тайминга — TIME_CRITICAL. EcoQoS и
   игнорирование `timeBeginPeriod` для фоновых процессов отключены: без этого
   в Windows 11 тайминг плывёт, как только фокус уходит в тестер.

**Почему именно > 700 Гц:** `km.device()` отдаёт `M:8uf`, то есть HID-интервал
мыши 1 мс, а потолок — 1000 Гц. Каждая команда должна попасть в свой USB-кадр.
Две команды в одном кадре суммируются в один отчёт, а пустой кадр отчёта не
даёт вовсе. Отсюда требования:
- скорость траектории ≥ ~1.5 пикс/мс, чтобы на каждом тике была ненулевая
  дельта (по умолчанию 2.0);
- равномерная отправка, что и даёт async.

## Что смотреть в консоли

- `команд/с` и `в драйвер/с` должны держаться на заданной частоте. Если они
  держатся, а тестер показывает меньше, — проблема на стороне прошивки, не ПК.
- `отложено`, `пропущено`, `фризов`, `опоздание` — здоровье потока и порта на ПК.
- `Путь: отправлено / пришло` — если мышь не трогали, должно СОВПАДАТЬ.

## Методика

Для каждого режима записывать частоту в тестере до касания, сразу после
касания и через 2–3 с после того, как рука убрана.
1. F1 и F2: разница между бинарным и текстовым путём.
2. F3 и F4 без касания: если при 250 Гц тестер всё равно показывает ~690, у
   прошивки свой таймер выхода.
3. F5 и F6: коснуться мыши на 1–2-й секунде; вернётся ли ~690 после
   ближайшей паузы.
4. F11 → 5 %, 10 %, 25 %, затем снова F1 с касанием. Spread размазывает
   команду по нескольким отчётам и может заполнять пустые кадры. Цена —
   задержка, поэтому интересны малые значения.

Дополнительно: `--spread N` (или F11) временно меняет mouse spread прошивки (live, без
NOR; при выходе возвращается). `--wait hybrid` снижает загрузку CPU ценой
джиттера. `--core N` закрепляет поток тайминга на ядре.
