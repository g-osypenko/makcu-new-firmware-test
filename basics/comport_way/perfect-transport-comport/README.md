# perfect-transport-comport: замороженный транспорт MAKCU (COM, Raw 0x69/0x6A)

Эталонный рабочий транспорт, вынесенный в одну папку, чтобы его можно было вставить в любую
программу и не путать с субстепперами, накопителями и рендерерами. Он **только доставляет**
целые отчёты `(dx, dy)` в MAKCU. Темп, нарезка траектории и квантование остаются на стороне
вызывающего кода.

**Не править.** Если нужна другая версия, создайте новую папку. Источник: `../makcu_transport.h`
(`RawComTransport`, `Format::RawMove`, `Mode::Async`) на 2026-10-10. Логика Raw перенесена
без изменений. Убраны только сравнительные форматы (`0x18`, `km.*`), sync-режим, SDK-транспорт
и зависимость от mak-suite SDK.

**Ревизия 2026-10-12 (2): кнопки мыши** (левая, правая, средняя, две боковые). Логика Raw-движения
не менялась, самопроверка движения после правки та же: 2000 = 2000 = 2000, отказов 0.

**Ревизия 2026-10-12 (3): инжект кнопок, блокировки, переподключение** — по образцу UDP-эталона
([`../../udp_way/perfect-transport-udp`](../../udp_way/perfect-transport-udp/README.md)), тот же API.
`press()`/`release()` всех пяти кнопок (без тайминга: время удержания задаёт вызывающий), блокировки
физического ввода (`setLock()`, 14 целей), сверка по снимку платы `0x56` и повтор потерянных команд,
автопереподключение после выдернутого USB2, сброс состояния при `open()` и `close()`. Логика
Raw-движения не менялась (после правки: 2000 = 2000 = 2000, отказов 0). Кольцо записи теперь под
мьютексом: кнопку можно нажать из любого потока, и она уходит сразу, не дожидаясь `move()`.

**Ревизия 2026-10-30 (5): курсор встаёт сразу, блокировки одной командой, отсчёты живой мыши** — то же,
что в UDP-эталоне ревизий 4–5, тот же API, оба заголовка собираются в одной программе.
- **Глубина очереди движения** `setMaxLag(n)`, по умолчанию 1. По COM очередь растёт не от заминок, а
  от расхождения часов: плата отдаёт запись на отчёт мыши, а её часы отстают от QPC примерно на 45 ppm.
  За 60 с движения хвост после последнего `move()` доходил до 3.6 мс, потолок ~10 мс. Теперь, если
  оценка очереди дошла до предела, дельта прибавляется к следующей записи: хвост **0.7–1.6 мс** и после
  60 с, склеивается 1 запись на ~4 с (0.03 %), путь точный.
- **`stopMovement()`**: «встать колом». Выбрасывается перенос, доигрывает то, что уже у платы. Курсор
  встаёт через **1.1 мс в медиане, max 1.6** (без руки на мыши, см. «Очередь движения и остановка»).
- **Блокировки направлений одной `0x16`**, колесо одной `0x17`, кнопки `0x60`. `setLocks({X, Y})`:
  физика встаёт через **0.42 мс в медиане, max 0.95**.
- **Отсчёты живой мыши** `setTracking(true)` / `physical()`: опрос позиции платы `GET 0x63` ~1700 раз/с,
  пока нет инжекта. Сумма совпадает с Raw Input до отсчёта, между опросами не больше одного отчёта мыши.
- Квитанции, перенос и пульс-снимок теперь дожимает сторожевой поток, если вызывающий молчит 3 мс. Пока
  он шлёт `move()`, всё идёт из его потока, рисунок записей на проводе как в ревизии 3.

**Известная проблема обеих ревизий:** при движении 1 кГц изредка пропадает пачка отчётов (32 или ~100–113 мс),
транспорт этого не видит, см. «Дыры в потоке отчётов».

## Использование

```cpp
#include "makcu_raw_transport.h"

makcu::RawTransport tx;
std::string err;
if (!tx.open("", err)) { /* "" - найти MAKCU самому; или "COM5" */ }

// поток тайминга, каждый тик (обычно 1 мс):
pendX += dx; pendY += dy;                      // ваш целый отчёт за тик
if ((pendX || pendY) && tx.move(int16_t(pendX), int16_t(pendY))) pendX = pendY = 0;
// move() == false - дельта остаётся в pend и уйдёт следующим тиком

tx.finish();   // конец движения: дождаться квитанций, дослать перенос (до 300 мс)
tx.close();
```

Кнопки (из любого потока, не блокируют):

```cpp
if (tx.buttonDown(makcu::MouseButton::Side2)) { /* боковая 2 зажата сейчас */ }
uint8_t mask = tx.buttons();                    // bit0 левая .. bit4 side2
uint32_t n = tx.pressCount(makcu::MouseButton::Left);  // нажатий с open(): разность = клики между чтениями
```

Инжект кнопок и блокировки (из любого потока, не блокируют):

```cpp
tx.press(makcu::MouseButton::Left);             // нажать; удержание - на вашей стороне (>= 3-5 мс)
tx.release(makcu::MouseButton::Left);           // отпустить
tx.setLock(makcu::LockTarget::Side2, true);     // side2 больше не доходит до игры, но buttons() её видит
tx.setLock(makcu::LockTarget::X, true);         // ось X физической мыши (оба направления)
tx.setLocks({makcu::LockTarget::X, makcu::LockTarget::Y}, true);  // обе оси ОДНОЙ командой: ~0.4 мс
tx.unlockAll();                                 // снять все блокировки
if (!tx.connected()) { /* USB2 пропал, транспорт переподключается сам */ }
```

Встать колом и отсчёты живой мыши (ревизия 5):

```cpp
tx.stopMovement();                              // инжект: курсор встаёт через ~1 мс, неотправленное выброшено
tx.setTracking(true);                           // опрос позиции платы, пока нет инжекта (km.screen 32767)
auto a = tx.physical();                         // a.x, a.y - отсчёты физической мыши; a.live - отрезок идёт
// ... мышь двигают ...
auto b = tx.physical();                         // b.x - a.x, b.y - a.y: движение руки между чтениями
tx.setTracking(false);                          // km.screen как было
```

## Контракт

| | |
| --- | --- |
| `open(port, err)` | `""` = первый CH343 `1A86:55D3`. Проба 4 000 000 / 1 000 000 / 115 200 бод по ответу `DEVICE 0x02`, DTR/RTS выкл., затем Raw: метаданные `0x6A(id=0)`, дочистка записей прошлых сессий, окно. `false` + причина: порт занят, плата не ответила, прошивка без Raw API |
| `move(dx, dy)` | **один принятый вызов = один HID-отчёт**; если очередь дошла до `maxLag`, дельта прибавляется к следующей записи (путь точный, `stats().merged`). Никогда не блокируется на USB (возможно короткое ожидание мьютекса, пока другой поток отправляет кнопку). `false` = окно (≤ 12 живых записей) или кольцо драйвера (32) заняты, или связи нет: дельту хранит вызывающий |
| `setMaxLag(n)` / `maxLag()` | глубина очереди движения, записей; по умолчанию 1, `0` — не ограничивать (как до ревизии 5). Оценка считается по времени, см. «Очередь движения и остановка». Замер: без предела за 60 с хвост 3.6 мс, с 1 — 1.5 мс, склеено 16 записей из 60 000 |
| `stopMovement(&dx, &dy)` | «встать колом»: перенос выброшен (сумма — в `dx`/`dy`, возвращает 0 или 1 запись: на COM отправка идёт сразу). Записи у платы доиграют, отозвать их нельзя. Курсор встаёт через 1.1 мс, max 1.6 |
| `setTracking(on)` / `tracking()` / `physical()` | отсчёты живой мыши по позиции платы `GET 0x63`: опрос каждые 0.5 мс, **только пока нет инжекта движения**; под полной блокировкой осей встаёт через 5 мс после подтверждения (позиция там не меняется). `physical()`: `x`, `y` — накопленные отсчёты с `setTracking(true)`, `samples`, `sampleQpc`, `live`. Первый `move()` закрывает отрезок, следующий начинается через 3.7–5.1 мс после последнего `move()`. Опрос `move()` не задерживает. На время слежения `km.screen` = 32767×32767 (запас ±16k отсчётов, перецентровка, когда мышь стоит), потом прежний. `setTracking(true)` блокирует на единицы мс |
| `move(0, 0)` / `service()` | на мышь ничего не уходит, только квитанции и перенос. Если вызывающий замолчал (3 мс), то же делает сторожевой поток |
| `finish(ms = 300)` | квитировать живые записи и дослать перенос. `true` = всё закрыто, перенос `(0,0)` |
| `stats()` / `statsLine()` | счётчики, можно вызывать из любого потока |
| `buttons()` / `buttonDown(b)` | маска физических кнопок (bit0 левая, 1 правая, 2 средняя, 3 side1, 4 side2). Любой поток, не блокируют. Обновляется событием `0x53` сразу по изменению |
| `pressCount(b)` | нажатий (переходов 0 → 1) с `open()`. Клик не теряется, даже если `buttons()` читают редко. Кнопка, зажатая уже при `open()`, нажатием не считается |
| `pollButtons()` | перечитать маску `0x55` (любой поток). Обычно не нужно: после переполнения потока транспорт перечитывает сам (в `move()`/`service()` или сторожем за ≤ 2 мс) |
| `press(b)` / `release(b)` / `setButtonState(b, down)` / `releaseAllButtons()` | инжект кнопки (`SET 0x11…0x15`). Уходит **сразу из вызывающего потока** одной записью вместе со снимком-проверкой, движение не ждёт. Замер: от `press()` до события в Windows 0.75–1.19 мс в среднем, max 1.34 мс. Инжект складывается с физикой (ИЛИ) |
| `injectedButtons()` / `injectedButtonsOnBoard()` | запрошенная маска инжектированных кнопок / что на плате по последнему снимку |
| `setLock(t, on)` / `setLocks({t…}, on)` / `unlockAll()` / `locked(t)` / `locks()` / `locksOnBoard()` | блокировка физического ввода: 5 кнопок, оси X/Y и колесо целиком или по направлению. Направления движения — одной `SET 0x16`, колесо — одной `0x17`, кнопки — `SET 0x60`. Заблокированное не доходит до ПК от физической мыши; инжект проходит; `buttons()` видит физику и у заблокированной кнопки. **Обе оси — через `setLocks({X, Y}, on)`**: одна команда, физика встаёт через 0.42 мс (max 0.95). Два вызова `setLock` подряд — 0.53 мс (max 1.27) |
| `controlsVerified()` | `false` — плата не ответила на снимок `0x56`: команды уходят без проверки |
| `connected()` / `healthy()` | связь с платой есть. `false` — идёт переподключение, `move()` возвращает `false` |
| `firmware()` | версия прошивки (`FIRMWARE 0x04`), `0` — не ответила |
| `open()` | дополнительно: снимает инжектированные кнопки и блокировки, оставшиеся от упавшей программы |
| `close()` | отпускает все инжектированные кнопки, снимает все блокировки (с подтверждением снимком), возвращает поток `INPUT_STREAM mouse` в состояние до `open()` |
| потоки | `move`/`service`/`finish` вызываются **из одного потока**. Остальное — из любого. Внутри поток чтения и сторожевой поток (тик 2 мс, при слежении 0.5 мс) |
| перенос | клампинг > 32767, склейка и отказы платы транспорт возвращает в перенос сам: путь не теряется |

Чего транспорт **не** делает: не держит часы и темп, не нарезает траекторию, не копит дробные
дельты и не добавляет шум. Частота HID равна частоте ненулевых принятых `move()` и не выше опроса USB
клонированной мыши.

## Кнопки мыши

`open()` включает поток событий `INPUT_STREAM mouse` (`0x52 01 01`), затем читает стартовую маску
`GET PHYS_BUTTONS 0x55` (V4.036+). Дальше поток чтения разбирает события
`DE AD 03 00 53 01 <id> <0|1>` и держит маску. Событие `53 01 FF FF` значит, что события потеряны:
транспорт перечитывает маску через `0x55` в ближайшем `move()`/`service()`. Если программа долго не
зовёт ни то, ни другое, после переполнения маска может отставать до следующего события.

### Ловушки, на которых ломается интеграция

- **Бинарные `0x11…0x15` (LEFT…SIDE2) физическую кнопку не видят.** Они возвращают только
  инжектированное состояние («софт держит кнопку»), поэтому физическое нажатие там всегда 0. Физику
  дают `0x55 PHYS_BUTTONS`, события `0x53` и текстовые `km.left()…km.side2()` (0 нет / 1 физ. / 2 инж. / 3 обе).
- **Старый поток `0x10 BUTTONS` не нужен.** В режимах 1/2 он вставляет в COM текст `km.<маска>\r\n` между
  бинарными кадрами (его включает SDK mak-suite при connect). Транспорт его не трогает и не разбирает.
- **Каждое включение потока `0x52` начинается с «всё отпущено».** Зажатая кнопка придёт событием только
  со следующим отчётом мыши, поэтому стартовую маску транспорт читает через `0x55` уже после включения.
- **По UDP события `0x53` приходят, но с «чужого» порта.** Плата шлёт их на порт клиента, а исходный порт
  ставит равным порту клиента, не 8080. Сокет с `connect()` такие датаграммы молча выбрасывает (поэтому
  первая проверка показала «0 событий»), а брандмауэр Windows на сети Public режет их для программы без
  разрешающего правила. UDP-транспорт сокет не подключает и страхуется опросом `0x55`.

## Очередь движения и остановка

Плата отдаёт в ПК одну запись на отчёт мыши, а программа шлёт одну запись в 1 мс. Часы разные, и у нас
плата отстаёт от QPC примерно на 45 ppm (видно и по сползанию фазы хвоста от прогона к прогону). Заминок
нет, но очередь всё равно растёт, на 1 запись за ~25 с непрерывного движения. Хвост после последнего
`move()`, мышь не трогали:

| Движение | Без предела | `setMaxLag(1)` |
| --- | --- | --- |
| 0.3 с | 0.84–1.00 мс | 1.00–1.21 мс |
| 1 с | 0.67–0.89 мс | 0.67–0.86 мс |
| 3 с | 1.42–1.49 мс | 1.31–1.60 мс |
| 10 с | 1.69–1.90 мс | 0.41–1.44 мс |
| 60 с | **3.56 мс** | **1.50 мс** |
| разгон: тик 999 мкс, 10 с | 10.6–10.8 мс | 0.82–0.94 мс |

Значения в первых строках различаются только фазой тика относительно отчёта мыши (0–1 мс). Правый
столбец до 10 с — со `stopMovement()`, остальное — от последнего `move()`.

**Почему квитанции очередь не показывают.** Запись получает `state 2`, когда отдана в USB-endpoint; контракт
Raw прямо говорит, что это не доказательство доставки. За FIFO есть ещё скрытый буфер примерно на
5 записей. Опыт с тиком 990 мкс: при хвосте 4.4–5.3 мс повторов ack 0 и живых записей 4, повторы появляются
с глубины ~6. Поэтому `0x6A` здесь не датчик.

**Как считается глубина.** `отправлено − отдано`, отдаётся запись в мс, с запасом 200 ppm на отставание часов
платы (`kRawClockDrift`). Запас больше реального отставания, так что истинная очередь не копится, а платим
склейкой раз в ~4–5 с. Нажатие и отпускание инжектированной кнопки — свой отчёт HID, он занимает слот записи
(сообщений Raw Input больше записей ровно на столько), поэтому оценка прибавляет их тоже. Страховка на случай
неверной оценки (отчёты физики, мышь медленнее 1 кГц): живые записи сверх обычных 4, через тик, потому что
квитанции уходят только с записью движения. Склейка = дельта уходит в перенос и прибавляется к следующей
записи; на таком тике в порт ничего не пишется. Если вызывающий замолчал, перенос дошлёт сторож (хвост
в этом редком случае до ~5 мс: 1 завершение из ~5000).

Клики и блокировки на ходу (`--busy --mark`, клик раз в 2 с, блокировка X+Y на 0.5 с раз в 10 с, мышь не
трогали), хвост и повторы ack на прогон 20 с: ревизия 3 — 3.7–9.3 мс (медиана 7.9), 15–22 тыс. повторов;
ревизия 5 — **0.52–1.48 мс (медиана 0.99)**, 0 повторов.

Выбор предела (разгон 1000 ppm и 60 с обычного тика):

| `setMaxLag` | Хвост при разгоне | Хвост за 60 с | Склеено за 60 с |
| --- | --- | --- | --- |
| 0 | 4.4–10.8 мс | 3.56 мс | 0 |
| **1** | **0.8–1.6 мс** | **1.50 мс** | 16 |
| 2 | 1.7–2.0 мс | 1.59 мс | 15 |
| 3 | 1.9–2.9 мс | — | — |

**Ограничение: рука на мыши.** Если физическая мышь движется во время инжекта, хвост **4.5–5.4 мс**, и
`setMaxLag` его не снижает (`--mark`, 1 и 0 дали одно и то же). Физические отчёты занимают слоты HID,
записи ждут, очередь дорастает до скрытого буфера и там насыщается: 1 лишний физический отчёт даёт хвост
2.8 мс, 4 — 5.1 мс. Дальше не растёт, по контракту Raw запись складывается с физическим смещением.
Держать очередь ниже насыщения можно только постоянной склейкой, то есть ценой плавности инжекта при
движении, поэтому транспорт этого не делает. `stopMovement()` с рукой отдельно не мерили: выбрасывать
там нечего, механизм тот же.

### Дыры в потоке отчётов (открытая проблема, не решена)

При движении 1 кГц изредка пропадает пачка подряд идущих отчётов: записи ушли, в Windows их нет, дальше
поток идёт ровно. Путь расходится на потерянный участок. Это не рука на мыши: сообщений Raw Input меньше
записей (1000 → 971–972), а не больше. Транспорт этого не видит: плата даёт `state 2`, отказов и повторов 0.

| | Ревизия 3 | Ревизия 5 |
| --- | --- | --- |
| `--busy`, клики и блокировки на ходу | 2 дыры за 240 с | 4 дыры за 240 с |
| Всё движение без руки за 2026-10-30 | 2 дыры за ~506 с | 10 дыр за ~1530 с |

Разница в пределах случайности: это не регрессия ревизии 5. Что известно:
- длительности дискретны: **31.8–32.4 мс** (за дырой 2–3 быстрых сообщения) и **97.6–112.8 мс** (6 быстрых);
- не связаны с кликами и блокировками: одна пришлась на +0.52 с, до первого клика в прогоне;
- идут кучками: две в первых двух прогонах, потом минуты чисто. Чистые 5 минут `--soak` были, и дыра в
  минуте 2 соседнего такого же прогона тоже (−24,+69; столбец «записи−сообщения» появился уже после него);
- 2026-10-12 `--soak` шёл 14 минут с точным путём, так что либо это редкость, либо условия изменились.

**Где теряется, ПК или плата, не установлено.** Сначала виновником посчитали квитанции отдельными
записями между тиками: дыры исчезли на 350 с, но `--busy` на ревизии 3 это опроверг. Правка осталась, она
просто сохраняет рисунок записей ревизии 3. По UDP дыры так не искали. В V4.119+ заявлено исправление
замирания ввода «после потерянного внутреннего подтверждения», но связь с этим не проверена.

## Физическая мышь: `setTracking` / `physical()`

Плата ведёт позицию по отчётам, которые принял ПК. Сторожевой поток спрашивает её `GET 0x63` раз в 0.5 мс,
один опрос в полёте, и копит разности. Подряд можно и 6.3 кГц, потерь нет, но 2 кГц уже дают каждый
отчёт мыши отдельно. Опрос `move()` не задерживает: ответы по COM идут по порядку, ждать нечего.

- **Инжект.** Первая запись закрывает отрезок (опрос, ушедший до неё, ещё засчитывается). Следующий начинается,
  когда записи квитированы, а оценка очереди + 3 мс истекла: через 3.7–5.1 мс после последнего `move()`.
- **Блокировка.** Под полной блокировкой осей позиция стоит (0 отсчётов за 400 мс с рукой на мыши), опрос
  встаёт через 5 мс после подтверждения снимком.
- **`km.screen`.** На время слежения 32767×32767, запас ±16k отсчётов. `SET 0x64` проверяется ответом
  `GET 0x64` в той же записи. Перецентровка: мышь стоит 5 мс и позиция ушла на 8000, или сразу на 14000.
  При обрыве связи восстанавливается. **Если программа упала, `km.screen` останется 32767×32767** до
  перезагрузки платы или следующего `km.screen`: `open()` исходный размер не знает.

## Инжект кнопок и блокировки

Команды `SET 0x11…0x15` (кнопки), `SET 0x16`/`0x17` (маски движения и колеса) и `SET 0x60` (блокировки)
у платы **без ответа** — и по COM тоже
(проба: за 50 мс ни одного кадра). Чем COM отличается от UDP (замеры 2026-10-12, fw 4097):

- **пауза после команды не нужна.** `SET` → пауза 0…2 мс → `GET 0x56`: 300/300 при любой паузе;
  `SET` → `SET` без паузы: 300/300 (по UDP следующая команда раньше ~1 мс молча теряется);
- **но `SET` изредка теряется**: 0.3–0.7 % в одних прогонах, до 12 % кучкой в другом; перечитывание
  через 30 мс подтверждает, что команда не применилась, а не применилась поздно. Причина не выяснена.
  2026-10-30 не воспроизвелось: 2958 попыток блокировки X+Y (4×`0x60` одной записью или с паузой 1 и 3 мс,
  одна `0x16`), с опросом `0x63` перед командой и без него, с рукой на мыши — все дошли. Условия потерь
  по UDP к COM не относятся. Сверка снимком остаётся;
- **снимок `GET 0x56 INJECT_SNAPSHOT`** по COM — те же 40 байт (`[0]` инжект-кнопки, `[1..2]` маска
  блокировок), ответ за ~0.3 мс (max 0.62).

Поэтому транспорт отправляет все различия «запрошено ↔ отправлено» и `GET 0x56` **одной записью
WriteFile** сразу из потока, который вызвал `press()`/`setLock()`. Ответы по COM приходят по порядку
запросов, так что снимок сопоставляется со своей записью без nonce. Если на плате не то, что отправлено,
разница уходит заново (`stats().repairs`). Пульс-снимок — раз в 250 мс.

Транспорт хранит **запрошенное** состояние, а не очередь команд. `press()` и сразу `release()` уйдут
обе, но если попадут между двумя опросами USB (1 мс), Windows клика не увидит: **удерживайте кнопку
хотя бы 3–5 мс** (тесты держат 40 мс).

**Оси в блокировках.** У платы по каждой оси два бита, «+» и «−». Бит оси целиком (`X`, `Y`, `Wheel`)
плата выставляет сама, когда заблокированы оба направления. Поэтому `setLock(X, on)` ставит или
снимает оба направления, а `setLock(XPos, false)` при заблокированной оси оставляет только −X.

**Блокировка движения одной командой.** `SET MOVE_MASK 0x16 left right down up` — те же биты 7, 6, 9, 10,
что у `0x60`, колесо `0x17 down up` — биты 13, 12. Транспорт отправляет все четыре направления одной
`0x16`, как только меняется любое из них. Задержка от вызова до последнего физического отсчёта в Windows
(рука водит кругами):

| Как | Медиана | Max | Утечка (отсчёты) |
| --- | --- | --- | --- |
| голая плата: 4×`0x60` одной записью (как ревизия 3) | 0.38 мс | 1.32 мс | 0–7 |
| голая плата: одна `0x16` | 0.14 мс | 1.01 мс | 0–5 |
| эталон: `setLock(X)` + `setLock(Y)` | 0.53 мс | 1.27 мс | 0–8 |
| эталон: `setLocks({X, Y})` | **0.42 мс** | **0.95 мс** | 0–10 |

Снимок подтверждает блокировку через 0.3–0.5 мс.

## Переподключение

Обрыв по COM — это выдернутый USB2 или пропавший порт (ошибка `WriteFile`/`ReadFile`), либо тишина:
нет ни одного байта от платы 750 мс при пульсе 250 мс. Тогда:

- `connected()` и `healthy()` дают `false`, `move()` возвращает `false`. Живые записи движения и перенос
  сбрасываются (`stats().droppedRecords`): к моменту восстановления они устарели;
- сторожевой поток закрывает хэндл и раз в 250 мс пробует открыть порт заново (тот же; при `open("")`
  — первый найденный MAKCU), подбирает скорость, `prepareRaw()` (id продолжаются, хвост записей
  дочищается), включает поток событий, перечитывает кнопки и по снимку досылает запрошенные блокировки
  и кнопки.

Если включено слежение, `connect()` заново задаёт `km.screen` (плата могла перезагрузиться) и начинает
новый отрезок.

Проверено владельцем 2026-10-12 (`controls_test --reconnect 60`, выдернутый USB2): связь
восстанавливается сама, блокировка на месте. Ревизия 5 (2026-10-30, `--reconnect 120`, слежение включено):
обрыв 5.3 с, связь вернулась сама, side2 заблокирована, слежение снова идёт, опросов 532 без потерь,
после закрытия `km.screen` 1920×1080.

**Ограничение.** Если в момент `close()` связи нет или программа упала, не дойдя до `close()`, зажатые
программой кнопки и блокировки **остаются на плате**: прошивка не отпускает их сама. Их снимет
следующий `open()` этого транспорта или перезагрузка платы. Ставьте обработчик Ctrl+C и закрытия
консоли, который вызывает `close()`.

## Требования

- Прошивка с Raw API: V4.074 и новее (проверено на **4094** и **4097**). На старой `open()` вернёт ошибку.
  Инжект и блокировки с проверкой снимком — прошивка с `0x56`/`0x60` (проверено на 4097).
- Мышь в host-порту MAKCU опрашивается на 1000 Гц: плата копирует её интервал опроса.
- COM-порт эксклюзивный: одновременно его может держать только одна программа.
- Сам транспорт «Повышенную точность указателя» не трогает. Для точного пути в Windows её выключает вызывающий.

## Протокол на проводе (для справки)

Кадр MAK_API: `DE AD | LEN u16 | CMD u8 | PAYLOAD`.

- `0x69 RAW_MOVE`: `id u32, x i16, y i16, timeout_uf u16 (0 = 1 с)` → `state u8, reason u8, id u32`.
  `1` = в FIFO; `255` = немедленная ошибка (`reason 3` = нет места, `4` = цель-мышь недоступна).
- `0x6A RAW_ACK`: `id u32, consume u8` → тот же ответ. `2` = отдано в USB-endpoint (это ещё не доставка в
  ПК: за FIFO буфер ~5 записей), `3` = отказ,
  `255/6` = ещё в очереди. `id = 0`: метаданные `schema, last_accepted_id, free_records, capacity (16)`.
- ID строго растут в пределах загрузки платы. Квитанция не раньше чем через 2 мс после отправки,
  повтор не чаще раза в 1 мс. Если ответа на `0x69` нет 50 мс, запись запрашивается через `0x6A`.
- `0x52 INPUT_STREAM`: `GET kind:u8` → `enabled:u8`; `SET kind:u8 enabled:u8` (без ответа). kind 1 = мышь.
- `0x53 INPUT_CHANGE` (незапрошенное): `kind:u8 id:u8 value:u8`, у мыши id = номер кнопки 0…4, value 0/1.
  `kind FF FF` = переполнение.
- `0x55 PHYS_BUTTONS` (V4.036+): пустой запрос → `mask:u8` физических кнопок.
- `0x11…0x15 LEFT…SIDE2`: `SET state:u8` (без ответа) — инжект; `GET` → только инжектированное состояние.
- `0x60 LOCK`: `SET target:u8 state:u8` (без ответа), цели 0…13 (кнопки, X/+X/−X, Y/+Y/−Y, колесо/+/−).
- `0x16 MOVE_MASK`: `SET left:u8 right:u8 down:u8 up:u8` (без ответа) = биты 7, 6, 9, 10. `0x17 WHEEL_MASK`:
  `SET down:u8 up:u8` (без ответа) = биты 13, 12.
- `0x63 GETPOS`: пустой запрос → `x:u16 y:u16`, позиция платы, зажата в `km.screen`. Ответ ~0.15 мс.
- `0x64 SCREEN`: пустой запрос → `w:u16 h:u16`; `SET w:u16 h:u16` (без ответа) ставит размер и позицию в центр.
- `0x56 INJECT_SNAPSHOT`: пустой запрос → 40 байт, `[0]` инжект-кнопки, `[1..2]` маска блокировок u16.
- `0x04 FIRMWARE`: пустой запрос → `u32` (4097).
