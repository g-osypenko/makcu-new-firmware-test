# perfect-transport-comport: замороженный транспорт MAKCU (COM, Raw 0x69/0x6A)

Эталонный рабочий транспорт, вынесенный в одну папку, чтобы его можно было вставить в любую
программу и не путать с субстепперами, накопителями и рендерерами. Он **только доставляет**
целые отчёты `(dx, dy)` в MAKCU. Темп, нарезка траектории и квантование остаются на стороне
вызывающего кода.

**Не править.** Если нужна другая версия, создайте новую папку. Источник: `../makcu_transport.h`
(`RawComTransport`, `Format::RawMove`, `Mode::Async`) на 2026-10-10. Логика Raw перенесена
без изменений. Убраны только сравнительные форматы (`0x18`, `km.*`), sync-режим, SDK-транспорт
и зависимость от mak-suite SDK.

**Ревизия 2026-10-12 (2): кнопки мыши** (левая, правая, средняя, две боковые). Логика Raw-движения
не менялась, самопроверка движения после правки та же: 2000 = 2000 = 2000, отказов 0.

**Ревизия 2026-10-12 (3): инжект кнопок, блокировки, переподключение** — по образцу UDP-эталона
([`../../udp_way/perfect-transport-udp`](../../udp_way/perfect-transport-udp/README.md)), тот же API.
`press()`/`release()` всех пяти кнопок (без тайминга: время удержания задаёт вызывающий), блокировки
физического ввода (`setLock()`, 14 целей), сверка по снимку платы `0x56` и повтор потерянных команд,
автопереподключение после выдернутого USB2, сброс состояния при `open()` и `close()`. Логика
Raw-движения не менялась (после правки: 2000 = 2000 = 2000, отказов 0). Кольцо записи теперь под
мьютексом: кнопку можно нажать из любого потока, и она уходит сразу, не дожидаясь `move()`.

## Использование

```cpp
#include "makcu_raw_transport.h"

makcu::RawTransport tx;
std::string err;
if (!tx.open("", err)) { /* "" - найти MAKCU самому; или "COM5" */ }

// поток тайминга, каждый тик (обычно 1 мс):
pendX += dx; pendY += dy;                      // ваш целый отчёт за тик
if ((pendX || pendY) && tx.move(int16_t(pendX), int16_t(pendY))) pendX = pendY = 0;
// move() == false - дельта остаётся в pend и уйдёт следующим тиком

tx.finish();   // конец движения: дождаться квитанций, дослать перенос (до 300 мс)
tx.close();
```

Кнопки (из любого потока, не блокируют):

```cpp
if (tx.buttonDown(makcu::MouseButton::Side2)) { /* боковая 2 зажата сейчас */ }
uint8_t mask = tx.buttons();                    // bit0 левая .. bit4 side2
uint32_t n = tx.pressCount(makcu::MouseButton::Left);  // нажатий с open(): разность = клики между чтениями
```

Инжект кнопок и блокировки (из любого потока, не блокируют):

```cpp
tx.press(makcu::MouseButton::Left);             // нажать; удержание - на вашей стороне (>= 3-5 мс)
tx.release(makcu::MouseButton::Left);           // отпустить
tx.setLock(makcu::LockTarget::Side2, true);     // side2 больше не доходит до игры, но buttons() её видит
tx.setLock(makcu::LockTarget::X, true);         // ось X физической мыши (оба направления)
tx.unlockAll();                                 // снять все блокировки
if (!tx.connected()) { /* USB2 пропал, транспорт переподключается сам */ }
```

## Контракт

| | |
| --- | --- |
| `open(port, err)` | `""` = первый CH343 `1A86:55D3`. Проба 4 000 000 / 1 000 000 / 115 200 бод по ответу `DEVICE 0x02`, DTR/RTS выкл., затем Raw: метаданные `0x6A(id=0)`, дочистка записей прошлых сессий, окно. `false` + причина: порт занят, плата не ответила, прошивка без Raw API |
| `move(dx, dy)` | **один принятый вызов = ровно один HID-отчёт**. Никогда не блокируется на USB (возможно короткое ожидание мьютекса, пока другой поток отправляет кнопку). `false` = окно (≤ 12 живых записей) или кольцо драйвера (32) заняты, или связи нет: дельту хранит вызывающий |
| `move(0, 0)` / `service()` | на мышь ничего не уходит, только квитанции и перенос |
| `finish(ms = 300)` | квитировать живые записи и дослать перенос. `true` = всё закрыто, перенос `(0,0)` |
| `stats()` / `statsLine()` | счётчики, можно вызывать из любого потока |
| `buttons()` / `buttonDown(b)` | маска физических кнопок (bit0 левая, 1 правая, 2 средняя, 3 side1, 4 side2). Любой поток, не блокируют. Обновляется событием `0x53` сразу по изменению |
| `pressCount(b)` | нажатий (переходов 0 → 1) с `open()`. Клик не теряется, даже если `buttons()` читают редко. Кнопка, зажатая уже при `open()`, нажатием не считается |
| `pollButtons()` | перечитать маску `0x55` (любой поток). Обычно не нужно: после переполнения потока транспорт перечитывает сам (в `move()`/`service()` или сторожем за ≤ 2 мс) |
| `press(b)` / `release(b)` / `setButtonState(b, down)` / `releaseAllButtons()` | инжект кнопки (`SET 0x11…0x15`). Уходит **сразу из вызывающего потока** одной записью вместе со снимком-проверкой, движение не ждёт. Замер: от `press()` до события в Windows 0.75–1.19 мс в среднем, max 1.34 мс. Инжект складывается с физикой (ИЛИ) |
| `injectedButtons()` / `injectedButtonsOnBoard()` | запрошенная маска инжектированных кнопок / что на плате по последнему снимку |
| `setLock(t, on)` / `setLocks({t…}, on)` / `unlockAll()` / `locked(t)` / `locks()` / `locksOnBoard()` | блокировка физического ввода (`SET LOCK 0x60`): 5 кнопок, оси X/Y и колесо целиком или по направлению. Заблокированное не доходит до ПК от физической мыши; инжект проходит; `buttons()` видит физику и у заблокированной кнопки. `setLocks` (2026-10-30, для одинакового API с UDP) ставит несколько целей одним вызовом — одной записью в порт. В UDP-эталоне направления движения уже уходят одной `0x16` (физика встаёт через ~1.3 мс вместо 7.7). Здесь это пока не сделано: нужен кабель USB2 для проверки |
| `controlsVerified()` | `false` — плата не ответила на снимок `0x56`: команды уходят без проверки |
| `connected()` / `healthy()` | связь с платой есть. `false` — идёт переподключение, `move()` возвращает `false` |
| `firmware()` | версия прошивки (`FIRMWARE 0x04`), `0` — не ответила |
| `open()` | дополнительно: снимает инжектированные кнопки и блокировки, оставшиеся от упавшей программы |
| `close()` | отпускает все инжектированные кнопки, снимает все блокировки (с подтверждением снимком), возвращает поток `INPUT_STREAM mouse` в состояние до `open()` |
| потоки | `move`/`service`/`finish` вызываются **из одного потока**. Остальное — из любого. Внутри поток чтения и сторожевой поток (тик 2 мс) |
| перенос | клампинг > 32767 и отказы платы транспорт возвращает в перенос сам: путь не теряется |

Чего транспорт **не** делает: не держит часы и темп, не нарезает траекторию, не копит дробные
дельты и не добавляет шум. Частота HID равна частоте ненулевых принятых `move()` и не выше опроса USB
клонированной мыши.

## Кнопки мыши

`open()` включает поток событий `INPUT_STREAM mouse` (`0x52 01 01`), затем читает стартовую маску
`GET PHYS_BUTTONS 0x55` (V4.036+). Дальше поток чтения разбирает события
`DE AD 03 00 53 01 <id> <0|1>` и держит маску. Событие `53 01 FF FF` значит, что события потеряны:
транспорт перечитывает маску через `0x55` в ближайшем `move()`/`service()`. Если программа долго не
зовёт ни то, ни другое, после переполнения маска может отставать до следующего события.

### Ловушки, на которых ломается интеграция

- **Бинарные `0x11…0x15` (LEFT…SIDE2) физическую кнопку не видят.** Они возвращают только
  инжектированное состояние («софт держит кнопку»), поэтому физическое нажатие там всегда 0. Физику
  дают `0x55 PHYS_BUTTONS`, события `0x53` и текстовые `km.left()…km.side2()` (0 нет / 1 физ. / 2 инж. / 3 обе).
- **Старый поток `0x10 BUTTONS` не нужен.** В режимах 1/2 он вставляет в COM текст `km.<маска>\r\n` между
  бинарными кадрами (его включает SDK mak-suite при connect). Транспорт его не трогает и не разбирает.
- **Каждое включение потока `0x52` начинается с «всё отпущено».** Зажатая кнопка придёт событием только
  со следующим отчётом мыши, поэтому стартовую маску транспорт читает через `0x55` уже после включения.
- **По UDP события `0x53` приходят, но с «чужого» порта.** Плата шлёт их на порт клиента, а исходный порт
  ставит равным порту клиента, не 8080. Сокет с `connect()` такие датаграммы молча выбрасывает (поэтому
  первая проверка показала «0 событий»), а брандмауэр Windows на сети Public режет их для программы без
  разрешающего правила. UDP-транспорт сокет не подключает и страхуется опросом `0x55`.

## Инжект кнопок и блокировки

Команды `SET 0x11…0x15` (кнопки) и `SET 0x60` (блокировки) у платы **без ответа** — и по COM тоже
(проба: за 50 мс ни одного кадра). Чем COM отличается от UDP (замеры 2026-10-12, fw 4097):

- **пауза после команды не нужна.** `SET` → пауза 0…2 мс → `GET 0x56`: 300/300 при любой паузе;
  `SET` → `SET` без паузы: 300/300 (по UDP следующая команда раньше ~1 мс молча теряется);
- **но `SET` изредка теряется**: 0.3–0.7 % в одних прогонах, до 12 % кучкой в другом; перечитывание
  через 30 мс подтверждает, что команда не применилась, а не применилась поздно. Причина не выяснена;
- **снимок `GET 0x56 INJECT_SNAPSHOT`** по COM — те же 40 байт (`[0]` инжект-кнопки, `[1..2]` маска
  блокировок), ответ за ~0.3 мс (max 0.62).

Поэтому транспорт отправляет все различия «запрошено ↔ отправлено» и `GET 0x56` **одной записью
WriteFile** сразу из потока, который вызвал `press()`/`setLock()`. Ответы по COM приходят по порядку
запросов, так что снимок сопоставляется со своей записью без nonce. Если на плате не то, что отправлено,
разница уходит заново (`stats().repairs`). Пульс-снимок — раз в 250 мс.

Транспорт хранит **запрошенное** состояние, а не очередь команд. `press()` и сразу `release()` уйдут
обе, но если попадут между двумя опросами USB (1 мс), Windows клика не увидит: **удерживайте кнопку
хотя бы 3–5 мс** (тесты держат 40 мс).

**Оси в блокировках.** У платы по каждой оси два бита, «+» и «−». Бит оси целиком (`X`, `Y`, `Wheel`)
плата выставляет сама, когда заблокированы оба направления. Поэтому `setLock(X, on)` ставит или
снимает оба направления, а `setLock(XPos, false)` при заблокированной оси оставляет только −X.

## Переподключение

Обрыв по COM — это выдернутый USB2 или пропавший порт (ошибка `WriteFile`/`ReadFile`), либо тишина:
нет ни одного байта от платы 750 мс при пульсе 250 мс. Тогда:

- `connected()` и `healthy()` дают `false`, `move()` возвращает `false`. Живые записи движения и перенос
  сбрасываются (`stats().droppedRecords`): к моменту восстановления они устарели;
- сторожевой поток закрывает хэндл и раз в 250 мс пробует открыть порт заново (тот же; при `open("")`
  — первый найденный MAKCU), подбирает скорость, `prepareRaw()` (id продолжаются, хвост записей
  дочищается), включает поток событий, перечитывает кнопки и по снимку досылает запрошенные блокировки
  и кнопки.

Проверено владельцем 2026-10-12 (`controls_test --reconnect 60`, выдернутый USB2): связь
восстанавливается сама, блокировка на месте. Длительность восстановления не записана.

**Ограничение.** Если в момент `close()` связи нет или программа упала, не дойдя до `close()`, зажатые
программой кнопки и блокировки **остаются на плате**: прошивка не отпускает их сама. Их снимет
следующий `open()` этого транспорта или перезагрузка платы. Ставьте обработчик Ctrl+C и закрытия
консоли, который вызывает `close()`.

## Требования

- Прошивка с Raw API: V4.074 и новее (проверено на **4094** и **4097**). На старой `open()` вернёт ошибку.
  Инжект и блокировки с проверкой снимком — прошивка с `0x56`/`0x60` (проверено на 4097).
- Мышь в host-порту MAKCU опрашивается на 1000 Гц: плата копирует её интервал опроса.
- COM-порт эксклюзивный: одновременно его может держать только одна программа.
- Сам транспорт «Повышенную точность указателя» не трогает. Для точного пути в Windows её выключает вызывающий.

любого окна или крестик окна — корректный выход (кнопки отпускаются, блокировки снимаются).

## Протокол на проводе (для справки)

Кадр MAK_API: `DE AD | LEN u16 | CMD u8 | PAYLOAD`.

- `0x69 RAW_MOVE`: `id u32, x i16, y i16, timeout_uf u16 (0 = 1 с)` → `state u8, reason u8, id u32`.
  `1` = в FIFO; `255` = немедленная ошибка (`reason 3` = нет места).
- `0x6A RAW_ACK`: `id u32, consume u8` → тот же ответ. `2` = отдано в USB-endpoint, `3` = отказ,
  `255/6` = ещё в очереди. `id = 0`: метаданные `schema, last_accepted_id, free_records, capacity (16)`.
- ID строго растут в пределах загрузки платы. Квитанция не раньше чем через 2 мс после отправки,
  повтор не чаще раза в 1 мс. Если ответа на `0x69` нет 50 мс, запись запрашивается через `0x6A`.
- `0x52 INPUT_STREAM`: `GET kind:u8` → `enabled:u8`; `SET kind:u8 enabled:u8` (без ответа). kind 1 = мышь.
- `0x53 INPUT_CHANGE` (незапрошенное): `kind:u8 id:u8 value:u8`, у мыши id = номер кнопки 0…4, value 0/1.
  `kind FF FF` = переполнение.
- `0x55 PHYS_BUTTONS` (V4.036+): пустой запрос → `mask:u8` физических кнопок.
- `0x11…0x15 LEFT…SIDE2`: `SET state:u8` (без ответа) — инжект; `GET` → только инжектированное состояние.
- `0x60 LOCK`: `SET target:u8 state:u8` (без ответа), цели 0…13 (кнопки, X/+X/−X, Y/+Y/−Y, колесо/+/−).
- `0x56 INJECT_SNAPSHOT`: пустой запрос → 40 байт, `[0]` инжект-кнопки, `[1..2]` маска блокировок u16.
- `0x04 FIRMWARE`: пустой запрос → `u32` (4097).
